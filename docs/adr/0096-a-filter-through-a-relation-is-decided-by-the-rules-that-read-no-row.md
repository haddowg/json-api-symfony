# A filter through a relation is decided by the rules that read no row

One filter matches every candidate parent at once, so whether the caller may reach through a relation has to be answered without a row. The relation's read permission decides when it declares one, as it does at the relation's endpoints, and an expression that reads `object` or `subject` refuses the filter for everyone, because no single answer holds for every parent and a query can't evaluate it per row. Otherwise the related type's `securityList` decides, as `GET /{type}` does, plus a `securityRead` that never reads the row; a read gate that reads the row is left to the type's query scope, as on its own collection, rather than refusing every filter through a type whose rows are read one by one. Each hop's Doctrine extensions run under `QueryPurpose::FetchRelatedCollection`, not a new purpose, so an extension written for the related endpoint scopes the filter without changes.
