# A relation declared with a foreign key is read and written by its related type's provider and persister

A to-many on a parent no Doctrine entity maps, such as a singleton a custom provider serves, failed on every read, because the related read scoped by the parent's own mapping and asked Doctrine for the metadata of a class it doesn't map. A relation declared with a foreign key is now always read by the related type's provider through `ReadsByForeignKeyInterface`, handed the page of parents keyed by wire id with the keys their rows hold, so it pushes down one `WHERE <foreign key> IN (:keys)` query under its own scope and windows it per parent, whatever provider serves the parents and whatever the parent model holds. Its relationship writes go to the related type's persister through `WritesForeignKeysInterface`, which sets the key on the rows joining the parent and clears it on the rows leaving, since the parent's persister has no column to write; the handler works out both sets from the linkage and the members the reads serve, so the scope, the gates, the hooks and the transaction behave as for any relationship write. A to-many with no foreign key on a type no entity maps reads what the parent model holds, cut in memory, as it did before every rendered to-many was paged, and is refused at warm-up only where that read can't be scoped: into a type a query extension scopes.
