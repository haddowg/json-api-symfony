# A server may declare its own response-header defaults

The `json_api.defaults` cache, deprecation and sunset headers applied to every server, so an app running two API versions side by side could deprecate the old one only by declaring the same `deprecation` and `sunset` on every resource class it serves. Each named server now takes the same `defaults` block under `json_api.servers.<name>`, built from one shared config node so it accepts and rejects the same values, and the `ResponseHeadersRegistry` resolves each value from the resource's own declaration, then its server's block, then the global one. The layers merge key by key with the existing `mergeOver`, so a server that sets only a sunset keeps the global deprecation, and cache directives keep their merge: unset values inherit, `no_cache` and `must_revalidate` switch on at any layer, and `vary` lists add up. We kept the global block as the fallback for every server, rather than making a server's block replace it whole, because the reason to add one is to change a header or two for a single version. The implicit `default` server has no block of its own, since the top-level `defaults` already is one. The OpenAPI projection describes none of these headers or a deprecated flag, so the documents don't change.

## Consequences

The shared node also tightens the global block: a `deprecation` that is neither a boolean nor a string, or a `sunset` or `sunset_link` that is not a string, now fails the build where it used to emit no header without saying why. YAML reads an unquoted date such as `2027-05-01` as an integer, so that value has to be quoted.
