# Response headers and action tags are keyed by server and type

The `ResponseHeadersRegistry` keyed each resource's `cacheHeaders`, `deprecation` and `sunset` by type name alone, and an untagged custom action inherited its mount type's OpenAPI tags from a map keyed the same way, so when two servers served the same type through different resource classes the last class read won on both servers. As with security in ADR 0142, each class's headers are now recorded under the server and type it belongs to, a class on several servers is recorded under each, and the response listener reads the entry for the request's `_jsonapi_server`, falling back to the default server; a server whose class declares nothing gets the global `json_api.defaults`. An untagged action takes the tags of the mount type's resource on each server it is served on, and the humanized-type default where that resource declares none. Resource tags were already read per server, and the OpenAPI projection documents none of the response headers, so neither changes.

## Update

The same keying now covers the rest of what a resource class or standalone capability declares. The `ResourceDescriptionRegistry` holds descriptions, operation descriptions, `singular` and vendor extensions per server and type, where it had merged them key by key across classes. A custom action mounts under the `uriType` of its type's descriptor on each server it is served on, and the route descriptors are built per server only, with no type-keyed map in between. Standalone serializers and hydrators are collected per server and type, where one class per type had served every server, and the write-capability check runs against each server's descriptors. In each case a server whose class declares nothing gets the default rather than another server's value.
